# Справочник истории версий (`versionHistory.json`)

Файл кормит кнопку «Сборка», превью в главном меню и полное окно истории.  
Читатель — **игрок**, не разработчик. Этот документ — для нас и для будущего себя, чтобы тон не сползал обратно в внутренний журнал.

Связанные файлы:

| Файл | Назначение |
|------|------------|
| `versionHistory.json` | Данные сборок |
| `versionHistory.js` | Превью, пагинация, кнопка, скрытие при диалоге NPC |
| `versionHistory.css` | Стили кнопки, превью, детального окна |

---

## Кто читает текст

Игрок, который открыл меню и хочет понять: *что в этой сборке изменилось для меня в игре*.

Не пишем:

- имена файлов и модулей (`unitFlight.js`, `firmScroll`, `save v2.3`);
- поля JSON и айди (`STAT_ROCKET_THRUST`, `openModalOnStart`, `3ZC`);
- внутренние версии подсистем («сохранения v2.2»);
- баги, которые игрок не видел, и правки «под капотом», если снаружи ничего не изменилось;
- списки всего, что трогали за спринт.

Пишем:

- новые места, куда можно пойти;
- новые действия, которые можно сделать;
- правила, которые игрок обязан понять (склад кончился — рецепт встал; без обсерватории дальние миры скрыты).

## Поля файла

### Корень

| Поле | Тип | Правило |
|------|-----|---------|
| `meta.currentBuild` | строка | Номер **текущей** сборки, как на кнопке. Всегда равен первой записи в `builds` и корневому `currentBuild`. |
| `meta.previewAvatar` | путь | Селезнев над превью в главном меню. Не класть это в записи сборок. |
| `typeImages.patch / update / major` | путь | Картинка типа обновления в рамке превью и в детальном окне. |
| `builds` | массив | **Новые сборки — в начало массива.** Первая = текущая = превью. |
| `currentBuild` | строка | Дубль `meta.currentBuild` (кнопка читает оба). Держать синхронно. |

### Запись сборки

| Поле | Тип | Правило |
|------|-----|---------|
| `id` | строка | Стабильный id, например `b017`. Не переиспользовать. |
| `build` | строка | Номер. Пока проект в ранней альфе — только `0.1.x`. До `0.2` не прыгаем. |
| `date` | `YYYY-MM-DD` | Дата публикации сборки (внутриигровой лор не подставлять). |
| `type` | `patch` \| `update` \| `major` | См. ниже. От него берётся картинка типа. |
| `title` | `{ ru, en, de }` | Короткий заголовок, 3–8 слов. Без номера сборки (номер уже рисуется отдельно). |
| `description` | `{ ru, en, de }` | Текст для игрока. 2–4 коротких абзаца. Абзацы через `\n\n`. |

**Запрещено** класть поле `image` в запись сборки: превью тогда ломается. Картинка типа берётся из `typeImages`.

Старые записи **не удаляем**. Можно переписать формулировки под игрока, но номер, дату и тип оставляем, если не было ошибки в фактах.

---

## Типы сборок

| `type` | Когда |
|--------|--------|
| `patch` | Узкий набор: баланс, тексты, понятный фикс того, что игрок уже видит. Нет нового «места» в игре. |
| `update` | Обычная поставка: одно-два крупных места плюс связанное. Большинство `0.1.x`. |
| `major` | Редкий рубеж. Пока только `0.1.0` (первая публичная). `0.2.0` и выше — когда скажем отдельно. |

Картинка в рамке = тип, не «о чём сборка». Селезнев стоит **над** превью и только в главном меню.

## Как писать заголовок

- Имена мест и действий, которые игрок узнает в игре: «Галактика», «Технопорт», «Цепочки производства».
- Без канцелярита («реализован функционал», «произведён рефакторинг»).
- Три языка — три законченные фразы, не подстрочник словаря.
- Заголовок превью должен читаться с одной строки. Если не влезает — короче, не мельче шрифтом.

Хорошо: «Наука, карта планеты и план стройки»  
Плохо: «Tech tree + MAC/MAG + ResourceCosts + plannedConstruction inputs»

---

## Как писать описание

**Главное правило: пишет человек игроку, не разработчик разработчику.**  
Текст должен читаться вслух без паузы «а это что такое?». Если слово знает только тот, кто смотрит код — его нет в истории версий.

1. Сначала — самое крупное изменение сборки (новое место или новое правило), **своими словами игрока**.
2. Затем — одно-два следствия, которые он заметит в ту же сессию.
3. Мелочи, которые не меняют поведение, отбрасываем.
4. Если правок много, **группируем** («на планете», «в космосе», «в колонии»), а не перечисляем двадцать тире.
5. Можно два-три абзаца. Стена из одной каши — нет.
6. Имена собственные как в игре: Святая Русь, Космисты, Буран, Вознесение: Эпоха-6.
7. Числа — только те, что игрок видит (кВт, километры обзора). Не пишем внутренние множители и айди рецептов.
8. Баги упоминаем одной фразой и только если игрок их ловил («Новая игра больше не поднимает прошлое сохранение»).
9. Консоль разработчика, отладочные клавиши, имена файлов — не в историю версий.
10. `ru`, `en`, `de` пишем сами, смысл один, ритм живой. Не копировать русский через переводчик слово в слово, если в языке так не говорят.

### Простой язык — обязателен

Пишем так, будто объясняем другу, который в игру зашёл вечером:

- «окно Наука», «карточка технологии», «список зданий» — да.
- «ярус», «ветка», «родители по уровню», «фирменный ползунок», «контейнер», «модалка», «ховер», «патч под капотом» — нет.
- Не перечисляем внутреннюю структуру («два яруса: базовое / продвинутое → физика… вплоть до…»). Говорим, что появилось и что с этим делать.
- Проверка: можно ли фразу понять, не открывая код и не зная, как устроен интерфейс. Если нет — переписать.

Плохо: «В фундаментальных науках два яруса; дочерние карточки требуют родителей; списки листаются фирменным скроллом.»  
Хорошо: «В окне Наука появилось больше карточек. Сначала простые науки, потом физика и химия. Колёсико в карточке крутит список требований, а не карту сзади.»

Длина ориентира: превью показывает только **последнюю** сборку и умеет скроллиться. Всё равно не раздувать описание: игрок должен успеть прочесть его за полминуты.

## Номер сборки

- Живём в линейке `0.1.x`, пока не решим иначе.
- Каждая поставка в историю версий = +1 к патчу (`0.1.6` → `0.1.7`).
- Пропущенные номера (у нас нет `0.1.4`) не выдумываем задним числом.
- `meta.currentBuild`, корневой `currentBuild` и `builds[0].build` всегда совпадают.

---

## Порядок работы, когда выходит сборка

1. Собрать список изменений **глазами игрока** (что увидел / что смог сделать нового).
2. Выбросить служебное.
3. Выбрать `type`.
4. Написать `title` и `description` на трёх языках.
5. Вставить объект **в начало** `builds`.
6. Обновить оба `currentBuild`.
7. **Не** ставить `image` у записи.
8. Не сокращать и не выкидывать старые сборки.

## Примеры тона

Плохо:

> Дерево технологий: категории, исследование с пулом очков, требования родителей по уровням, графы-конвейеры, STAT_ROCKET_THRUST, unitSpaceSpeed.js.

Хорошо:

> Открылось дерево наук. Исследование идёт из общего потока технологий. Закрытые ветки видны как неизвестные карточки. От двигателя зависит, как быстро «Буран» летит между телами.

Плохо:

> save v2.3 techProgress + locationBuildings + playSegments.

Хорошо:

> В сохранение пишутся науки, здания и наигранное время. Слот можно перезаписать или положить рядом автосохранение.

---

## Превью и полное окно

- Превью в главном меню = **только** `builds[0]`.
- В рамке превью — картинка **типа** сборки (`typeImages`), не портрет.
- Селезнев — декорация над окном превью, в записи JSON его нет.
- Полное окно листает все `builds` по порядку массива.
- Кнопка «Сборка:» живёт в меню и в игре; при большом диалоге NPC скрывается.

Если после правки JSON превью пустое — скорее всего в запись снова попало поле `image`. Убрать.
